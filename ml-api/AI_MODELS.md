## Overview

When a user uploads a price file, it passes through two engines in order:

1. **Matching engine**: *"Which real product and which real market does this row mean?"* For example, "Irish potatos" becomes "Irish-potato", and "Karenje" becomes "Karenge".
2. **Anomaly engine**: *"Does this price make sense?"* It uses rules, statistics, and a trained machine-learning model called an Isolation Forest.

Every finding carries **evidence, a confidence score and a recommended action**, and is sent to the **Review Center**. A person decides; the models never silently change data.

```
CSV / JSON upload
  → ingest.py          detect columns, parse prices, dates, channel
  → matching engine    name → catalog entry (exact / auto / review / ambiguous / unknown / archived)
  → anomaly engine     4 layers → PRICE_ANOMALY, LADDER_VIOLATION, INVALID_PRICE
  → findings + coverage report → Review Center
```

## Step 0 — Reading the file

File: [`minagri_ai/ingest.py`](minagri_ai/ingest.py)

Before any model runs, the upload has to be understood:

- **Columns** are detected from common header names. For example, `price_type`, `channel`, `market_level` and `level` all mean *price channel*.
- **Channels** are normalised to `farmgate`, `wholesale` or `retail`. "farm gate", "producer price" and "bulk" are all recognised.
- **Prices** are cleaned, so `"1,200 RWF"` becomes `1200`.
- **Raw e-Soko JSON exports** are recognised and converted automatically.
- **Excel files** are rejected with a message asking for CSV.
- **Every row gets an id** (`rec-1`, `rec-2`, …) so every finding points back to its exact row.

## Engine 1 — Matching engine

File: [`minagri_ai/matching.py`](minagri_ai/matching.py)

### The problem

Field reporters type names by hand: "Irish potatos", "Nyabugogo Mkt", "Karenje", Kinyarwanda names such as "Ibirayi", and French names. The official e-Soko catalog has **133 commodities** and **67 markets**. Each typed name must be tied to exactly one of them, or flagged if it cannot be.

### Step by step

#### 1. Normalise

The text is lower-cased, accents and punctuation are removed, and spaces are tidied. For markets, the words `market`, `mkt`, `isoko` and `marche` are also stripped, so "Nyabugogo Mkt" becomes `nyabugogo`.

#### 2. Exact lookup

The name is checked against every catalog name and alias, including Kinyarwanda and French names.

- **One owner:** status `exact`, score 1.0. No model is needed.
- **Several owners:** status `ambiguous`. For example, "Amateke" is the local name for both Taro and Yams.

#### 3. Archived check

If the name belongs to a product e-Soko has archived (for example Yams), the status is `archived`. That means *"prices are still arriving for a product you retired."*

#### 4. RapidFuzz: spelling similarity

RapidFuzz is a fast string-similarity library. The score for each catalog entry is:

$$
\text{score} = \max(\text{ratio},\ \text{token\_sort},\ 0.95 \times \text{token\_set})
$$

| Component | Catches |
|---|---|
| `ratio` | Typos (edit distance): "Karenje" vs "Karenge" |
| `token_sort` | Word order: "potato irish" vs "Irish potato" |
| `token_set` | Extra words. Discounted to 95% so "maize" is not a perfect match for "maize flour" |

Every alias is scored, and each catalog entry keeps its best alias score.

#### 5. Sentence Transformer: meaning similarity

Model: [`paraphrase-multilingual-MiniLM-L12-v2`](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2), a small neural network trained on more than 50 languages.

- It turns any text into **384 numbers** (an *embedding*). Texts with similar meaning get similar numbers, and cosine similarity measures how close two embeddings are.
- It runs **only when RapidFuzz is below 92% confident**. Clear matches skip it, which keeps uploads fast.
- Catalog embeddings are computed once and cached in `models/embeddings/`.
- If the model cannot load, a lighter **TF-IDF** fallback (character 2–4-grams) is used instead. To force the fallback, set `MINAGRI_USE_SENTENCE_TRANSFORMER=0`.

How the two opinions are combined ($f$ is the RapidFuzz score, $e$ is the embedding score):

| Situation | What happens |
|---|---|
| Both models pick the same entry | Confidence is boosted to $\max(f,\ 0.5f + 0.5e)$ |
| The embedding prefers a different entry | Noted in the evidence. Its vote counts only if its preference exceeds the *veto margin* |
| RapidFuzz finds nothing, but the embedding recognises the meaning | Optional semantic suggestion (e.g. "Aubergine" → "Eggplant"). Testing showed **no net correct rescues**, so calibration switched it off (`embedding_suggest: null`) |

#### 6. Decision

The final score is compared with **calibrated** thresholds:

| | Auto-accept at or above | Send to review between | Unknown below |
|---|---|---|---|
| Commodity | 0.86 | 0.80 – 0.86 | 0.80 |
| Market | 0.85 | 0.69 – 0.85 | 0.69 |

If the top two candidates are **within 2 points** of each other, the status is `ambiguous` whatever the score. The model should not guess between near-equals.

### Match statuses

| Status | Meaning | Finding raised |
|---|---|---|
| `exact` | Name or alias matched exactly | None |
| `auto` | Above auto-accept, applied without review | None |
| `review` | Plausible match, needs a person | `ENTITY_MATCH` with a suggestion |
| `ambiguous` | Two or more entries fit equally well | `ENTITY_MATCH` listing the tied entries |
| `unknown` | Nothing close enough | `UNKNOWN_ENTITY` |
| `archived` | Product is archived in e-Soko | `ENTITY_MATCH` (archived) |
| `empty` | Blank value | None (completeness checks cover it) |

### How the thresholds were chosen

File: [`train.py`](train.py)

The thresholds are measured, not hand-picked:

- **Test set:** every catalog name plus **four generated misspellings** of each, giving 1,305 commodity cases and 335 market cases.
- **20 out-of-catalog names** that exist in neither registry. None may receive a suggestion.
- **About 40 hand-labelled phrasing variants.**

The script then searches for the thresholds that auto-accept the most rows with **zero wrong auto-accepts**. The results are saved in [`models/matching_calibration.json`](models/matching_calibration.json).

### Measured results

| | Correct top pick | Auto-accepted, RapidFuzz only | Auto-accepted, with embeddings | Wrong auto-accepts |
|---|---|---|---|---|
| Commodities | 99.9% | 84.4% | 86.3% | 0 |
| Markets | 99.4% | 84.2% | 87.2% | 0 |

- **The embeddings earn their place.** About 2 to 3% more rows pass without a person checking them, with no loss of precision.
- **Unknown names stay unknown.** None of the 20 invented names received a suggestion. Something like "Laptop" is reported as unknown rather than forced onto a product.
- **Weakest area: different wording.** On phrasing variants such as synonyms, the correct top pick is only 65%. When unsure, the model sends the name to review rather than guessing wrong.

## Engine 2 — Anomaly engine

Files: [`rules.py`](minagri_ai/rules.py), [`statistics.py`](minagri_ai/statistics.py), [`features.py`](minagri_ai/features.py), [`anomaly.py`](minagri_ai/anomaly.py)

It has four layers, because different kinds of errors need different tools.

### Layer 1: hard rules

A price of zero or below is flagged `INVALID_PRICE` with 97% confidence. No model is needed.

### Layer 2: robust statistics

Prices are compared only with their **peers**: the same commodity at the same price channel, across all markets. A retail tomato is never compared with a wholesale tomato or with beans. At least **5 peers** are required.

Two tests run, and **either one** can flag the price.

**Modified z-score** (Iglewicz & Hoaglin), using the median and the MAD (median absolute deviation) instead of the mean and standard deviation:

$$
z = \frac{0.6745\,(x - \text{median})}{\text{MAD}}
$$

*Why the median?* One typo like 12,000 instead of 1,200 would drag an ordinary mean upward and hide itself. The median barely moves. The price is flagged when $|z| \ge 3.5$.

If every peer has exactly the same price, the MAD is 0. The code then uses the interquartile range instead, and if that is also 0, it uses 5% of the median.

**IQR fence** (the classic box-plot rule): the price is flagged if it falls outside

$$
[\,Q_1 - 1.5 \cdot IQR,\ \ Q_3 + 1.5 \cdot IQR\,]
$$

Severity rises with $|z|$: **medium**, then **high** above 5, then **critical** above 8. The suggested correction is the peer median.

### Layer 3: context rules

These use economic common sense:

- **Price ladder:** for the same market, commodity and date, *farm gate ≤ wholesale ≤ retail* should hold. Wholesale above retail is flagged as `LADDER_VIOLATION`; a bigger inversion gives higher severity.
- **Markup:** retail more than **3 times** the farm-gate price is flagged as suspicious.

### Layer 4: the Isolation Forest (trained model)

#### How an Isolation Forest works

It builds **200 random decision trees**. Each tree repeatedly picks a random feature and a random split point until every data point sits alone.

- **Normal points** sit in dense crowds and need **many** splits to isolate.
- **Anomalies** are few and different, so they get isolated in **a few** splits.

The anomaly score comes from the average path length $E[h(x)]$ across all trees:

$$
s(x) = 2^{-\frac{E[h(x)]}{c(n)}}
$$

About **0.5 is ordinary**, and **close to 1 is very easy to isolate**. Each tree sees a random sample of **256 rows**, as recommended in the original paper (Liu, Ting & Zhou, 2008).

#### Why it doesn't use raw prices

A kilo of goat meat and one egg live on completely different price scales. Fed raw prices, the forest would simply learn "expensive items are anomalies". Instead, every row is described by **8 relative features**:

| # | Feature | What it captures |
|---|---|---|
| 1 | log(price / peer median) | Distance from the national norm for this commodity and channel |
| 2 | Robust z-score | The same, scaled by how variable this commodity is |
| 3 | Versus this market's usual level | Some markets (Kigali) are always pricier; this removes that |
| 4 | Versus this province's usual level | Same idea at province level |
| 5 | Price channel | Farm gate, wholesale or retail |
| 6 | log(retail / farm gate) | Is the markup normal? |
| 7 | log(wholesale / farm gate) | Same, for wholesale |
| 8 | log(retail / wholesale) | Same, retail over wholesale |

Using logs makes ×10 and ÷10 equally far from normal. When a comparison isn't possible (for example, no farm-gate price that day), the feature is filled with the typical value so it doesn't look strange.

#### Training

- **Data:** the real e-Soko snapshot, **1,096 priced rows** from 28 September 2026.
- **Library:** scikit-learn `IsolationForest(n_estimators=200, max_samples=256, random_state=42)`.
- **Review line:** the **97.5th percentile** of training scores, **0.621**. About 2.5% of normal data scores above it.
- **Saved to:** `models/price_iforest.joblib`. On load, the model is rejected if the feature list has changed since training.

#### Explaining the model's output

An Isolation Forest only says *"this is odd"*, not why. So for each flagged row, the code finds the **feature furthest from typical** and writes it in plain language, for example *"retail is +240% over farm gate (typical +30%)"*. A flag is dropped if no feature is meaningfully off.

#### Staying modest

- **When it agrees with Layer 2:** the flag counts as *corroborated* and strengthens the existing finding rather than creating a duplicate.
- **Its own new findings are capped at 5% of rows,** so a strange upload cannot flood the Review Center.

### Measured results (injected-error test)

`train.py` copies the real data, plants **320 known errors** (8 rounds × 40), and counts how many each layer catches:

| Error planted | Isolation Forest | Z-score | Ladder rule | All layers together |
|---|---|---|---|---|
| Extra zero (×10) | 87.5% | 70.0% | 100% | **100%** |
| Missing zero (÷10) | 80.0% | 53.8% | 98.8% | **100%** |
| +60% spike | 50.0% | 47.5% | 62.5% | **82.5%** |
| Wholesale above retail | 71.2% | 45.0% | 98.8% | **100%** |
| **Overall** | **72.2%** | **54.1%** | | **95.6%** |

**False alarms** on untouched rows: the forest alone flags **2.8%**, all layers together flag **5.8%**.

> **Takeaway:** no single method is good enough alone. The forest beats plain statistics by 18 points, but the **combination catches 95.6%** of errors. That is why the system is a hybrid.

## Design principles

1. **Every finding explains itself.** It lists the observed value, the expected range, the peer median and the model used. An officer sees *why*, not just "the AI says so".
2. **The models suggest; people decide.** Only very confident name matches (at least 85–86%, with zero measured errors) are applied automatically. Everything else goes to review.
3. **Reported accuracy is measured.** The numbers come from repeatable tests on real e-Soko data, stored in the model card and shown on the dashboard.
4. **Fallbacks keep it working:**
   - Without the Sentence Transformer, matching uses TF-IDF.
   - Without the Python API, the browser runs its own TypeScript versions of the models (`src/lib/minagri/ml/`).

---

## Limitations

- **Small training set.** 1,096 rows from a single snapshot. Seasonal patterns (prices rising before harvest) are not learned yet; that needs several months of history.
- **Moderate spikes are the hardest case.** A +60% jump is plausible for real price moves, so all layers together catch only 82.5%.
- **Synonyms are weak.** Different wording is picked correctly only 65% of the time. The model fails safely (sends to review), but a person must decide.
- **Coverage gaps aren't the models' fault.** The current data covers **11 of 67 markets**, and no Northern Province market reports prices. The coverage report surfaces this, but the models cannot fix missing data.

## Retraining

Run these from the repository root:

```bash
npm run ai:setup    # once: create ml-api/.venv and install requirements
npm run ai:train    # refit the forest, recalibrate matching, rewrite the model card
npm run ai:test     # run the API test suite
npm run ai:api      # start the API on http://127.0.0.1:5001
```

After retraining, call `POST /api/models/reload` or restart the server so it picks up the new model.
